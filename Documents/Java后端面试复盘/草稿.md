1. **登录 + JWT 鉴权**
   重点文件：

   * AuthController
   * AuthServiceImpl
   * JwtUtils
   * LoginCheckInterceptor
   * WebConfig
   * unitour-api.js

   你要搞清楚：

   #### 登录接口路径是什么？

   `api/v1/auth/login`

   ####  前端传什么参数？

   前端传递用户名和密码两个参数，绑定在 loginDto 类里面

   #### 后端怎么查用户？

   后端在 AuthServiceImpl 的 login 方法里面调用UserMapper 层里面的 selectByUsernameOrPhone 方法来查询用户，如果查到的用户为空或者用户状态不合法则会抛出异常提示账号或密码错误。

   ####  BCrypt 在哪里校验？

   使用 passwordEncoder 的方法 matches 方法将查到的用户的 password1和请求体中的 password 进行校验

   ####  JWT 在哪里生成？

   我在Utils 包里面定义了一个 JwtUtils 类，这个类有一个根据Payload 生成 JWT 的静态方法 generateToken （），在 login 方法里面直接调用这个静态方法同时传入自己指定的Payload就可以生成JWT

   ####  前端 token 放在哪里？

   前端的token放在请求头里，在拦截器中解析请求头即可

   #### 请求头 Authorization 怎么带？

   请求头是以`Bearer `开头的，后面是真正的token

   ####  拦截器怎么解析 token？

   拦截器首先从请求头中获取authorization，然后判断是不是空还有是不是以`Bearer `开头的，如果不是那么就返回未登录的结果。然后将这个authorization进行字符串截取得到真正的token，再通过JwtUtils中定义的parseToken的静态方法进行解析，得到里面Payload中的UserId部分，并将其写入request中，方便后续Controller知道当前用户的是谁。

   #### userId 怎么放进 request？

   首先通过JwtUtils中的parseToken的静态方法进行解析，得到载荷部分，这是一个HashMap类型的集合，然后获取集合中的 userId 的值，通过 setAttribute 方法放入请求request 中。

   #### 哪些接口被放行？

   

   #### 整体调用链：

   ```text
   前端输入账号（可以是用户名也可以是手机号）和密码发送登录请求
   
   ->AuthController 中的 login 方法接收请求
   ->AuthServiceImpl中的 login 方法校验参数
   ->UserMapper 里面的 selectByUsernameOrPhone 方法查询用户
   ->调用 BCrptPasswordEncoder 校验密码
   ->将 UserId、Username 放入载荷并调用 JwtUtils#generateToken方法生成JWT
   ->封装 LoginVO 并返回
   ->前端将 token 进行保存
   ->后续请求通过 Authorization: Bearer token 	携带 token
   ->请求在进入 Controller 之前被LoginCheckInterceptor#preHandle进行拦截
   ->JwtUtils 解析token 获得 claims
   ->从 claims 中获取 UserId 并调用 request.setAttribute("userId",userId)写入请求
   ->后续 Controller 可以从 request 中拿到 userId
   ```

### Redis 这块的理解：

我项目中 Redis 主要有两个使用场景

第一个是注册时验证码的存储，由于验证码是短生命周期数据，不适合存放在 MySQL 这种持久化的数据库中，而 Redis 中有 TTL，天然适合存储验证码这种数据，我给它设置了 5 分钟的过期时间。

第二个是高校详情缓存，由于高校详情这种数据是典型的读多写少的数据，用户会频繁地进行访问，而且它聚合了高校基础信息、校区列表、POI 列表、综合评价等多个模块，很适合用 Redis 来缓存，从而降低 MySQL 的查询压力并且增加查询效率。

注册验证码这块 Redis 的调用链路大概是：首先前端发送请求注册验证码的请求，AuthController 接收请求后调用 Service 层中的 generateRegisterCaptcha 方法，用 UUID 来生成一个 captchaId 然后使用 RedisConstant 类中的 key 拼接的方法来生成一个标准的 Redis 的 key，再生成一个 4 位验证码，使用 StringRedisTemplate 的ops.set（） 方法将 captchaId 和code 存入 Redis并设置 TTL 为 5 分钟，最后返回给前端。

用户注册时提交 captchaId 和 验证码，然后Service 层中根据 captchaId 来拼接 Redis 的 key，随后根据这个 key 查询 redis，将查到的结果与输入的进行匹配，如果查不到则说明验证码已过期，如果查到但不匹配说明验证码输错了返回验证码不正确，如果匹配成功，则删除 Redis key 防止重复使用。随后就继续执行注册的其他业务逻辑

在高校详情缓存这块，UniversityController 接收请求之后调用 UniversityService 中的getUniversityDetail 方法，先校验 universityId，然后要先拼接 key 来查 redis，如果查到就直接返回，返回之前要先反序列化成 UniversityDetailVO 对象，如果查不到再调用 UniversityMapper 中的selectUniversityById 方法来查询高校信息、校区列表、综合评分等最后对 UniversityDetailVO 进行组装，组装完成之后先将对象转 JSON 然后再存入 Redis，这里设置TTL 为 30 分钟，最后返回。

然后如果进行了新增评价、删除评价、上传校区图操作那么需要删除高校详情缓存，因为这些操作会影响到最终的详情数据，先到数据库中查最新数据重新写入 Redis 比较好。

这里的 Redis 我主要使用的是 String 类型的，没有使用 Hash 类型，因为高校详情中聚合了很多内容，使用 Hash 类型需要维护很多 filed 字段还要处理嵌套对象和列表结构，不太方便，对于当前项目结构来说使用 String 类型存储 JSON更直接。

还有我当前项目是个单体架构的项目，还没有做复杂的缓存击穿、穿透、雪崩等治理，后续如果访问量增加或者项目功能拓展我会对其进行升级，key 对空结果做短 TTL 缓存、给 TTL 增加随机时间、热点 key 加互斥锁等。

缓存穿透是指，请求访问的是 Redis 和数据库中都不存在的数据，请求每次都会打到数据库，可以进行缓存空值或者加布隆过滤器处理。

缓存击穿是指，同一个 key 在过期后的一瞬间，大量请求同时打到数据库，可以考虑添加互斥锁或者给热点 key 设置不过期或者考虑逻辑过期。

缓存雪崩是指大量的 key 同时过期，然后大量的请求同时打到数据库，可以考虑设置多级缓存、随机 TTL、提前预热等机制。

还有使用 Redis 之所以快是因为数据存储在内存当中，不需要磁盘 IO，而且其数据结构设计也非常高效，所以比较快。
