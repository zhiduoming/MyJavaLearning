### 项目 1 分钟讲解

我的项目叫 UniTour，是一个高校多维认知与择校辅助系统，主要面向择校场景，帮助学生从高校基础信息、校区差异、校园 POI、多维评分和用户真实评价等角度了解一所学校。

后端使用 Spring Boot、MyBatis、MySQL、Redis、JWT，文件上传使用阿里云 OSS，并部署到了自己的云服务器上。项目整体采用 Controller、Service、Mapper 分层，统一使用 Result 返回结果，并通过全局异常处理器统一处理异常。

我主要实现了用户注册登录、JWT 鉴权、高校列表和详情查询、校区 POI 展示、评价发布、回复、点赞、Redis 注册验证码、高校详情缓存、OSS 图片上传等功能。通过这个项目，我熟悉了后端接口开发、数据库表设计、MyBatis XML、Redis 使用和项目部署流程。

记忆骨架：项目定位 -> 技术栈 -> 核心功能 -> 项目收获。



### 为什么要做这个项目？

我做这个项目主要是因为很多学生在择校时只关注分数线、排名、专业这些信息，但对真实校园体验了解不多，比如不同校区的位置、宿舍、食堂、周边环境、校园设施、学习氛围等。

所以 UniTour 不是单纯做一个高校信息查询系统，而是希望从高校基础信息、校区差异、校园 POI、多维评分和用户评价这几个角度，帮助学生更全面地了解一所学校。



### 项目整体架构？

项目整体是一个单体 Spring Boot 后端项目，采用经典的 Controller、Service、Mapper 分层结构。

Controller 层负责接收前端请求、处理参数和返回统一结果；Service 层负责核心业务逻辑，比如注册登录、评价发布、缓存处理；Mapper 层通过 MyBatis XML 执行 SQL，操作 MySQL 数据库。

MySQL 负责存储用户、高校、校区、POI、评价、点赞、回复等核心数据。Redis 主要用于注册验证码和高校详情缓存。JWT 用于登录后的身份认证。阿里云 OSS 用于图片上传，数据库中只保存图片 URL。

记忆骨架：Controller -> Service -> Mapper -> MySQL；Redis 做验证码和缓存；JWT 做认证；OSS 做图片存储。



### 登录和 JWT 鉴权怎么实现？

用户登录时，前端提交账号和密码，后端先根据账号查询用户信息，然后使用 BCrypt 对密码进行校验。校验通过后，后端会生成一个 JWT 返回给前端。

前端后续访问需要登录的接口时，会在请求头的 Authorization 字段中携带这个 token。后端通过登录拦截器统一拦截请求，解析 JWT，校验 token 是否有效。如果解析成功，就从 token 中取出用户 ID，并放到 request 中，后续 Controller 或 Service 就可以知道当前登录用户是谁。

这样做的好处是不用在每个接口里重复写登录校验逻辑，而是把认证逻辑统一放到拦截器中处理。

调用链：登录请求 -> 查询用户 -> BCrypt 校验密码 -> 生成 JWT -> 前端携带 Authorization -> 拦截器解析 token -> userId 放入 request。

关键代码位置：AuthController、AuthServiceImpl、JwtUtils、LoginCheckInterceptor、WebConfig。



### JWT 登录鉴权代码复盘

登录接口路径是 `POST /api/v1/auth/login`。前端传入 `username` 和 `password`，绑定到 LoginDTO 中。这里的 `username` 实际上既支持用户名，也支持手机号。

后端在 AuthController 的 login 方法中接收请求，然后调用 AuthServiceImpl 的 login 方法。Service 层先校验参数，再调用 UserMapper 的 selectByUsernameOrPhone 方法查询用户。

如果用户不存在，或者用户状态不是正常状态，后端会统一返回“账号或密码错误”，而不是明确提示“账号不存在”或者“用户状态异常”。这样可以避免暴露过多账号细节，降低被枚举账号或撞库的风险。

密码校验使用 BCryptPasswordEncoder 的 matches 方法。前端传过来的是用户输入的明文密码，数据库中存的是 BCrypt 加密后的密码。登录时调用 `passwordEncoder.matches(dto.getPassword(), user.getPassword())` 来判断密码是否匹配。

校验通过后，后端会把 `userId` 和 `username` 放入 claims，然后调用 JwtUtils 的 generateToken 方法生成 JWT。生成 token 时还会通过 setExpiration 设置 12 小时过期时间，并使用服务端的 SECRET_KEY 做 HS256 签名。

注意：`userId` 和 `username` 是我手动放入 JWT claims 的业务字段；过期时间是 JWT 的标准字段；SECRET_KEY 不是放在 Payload 里的内容，而是服务端用于签名和校验 token 是否被篡改的密钥。

前端拿到 LoginVO 之后，会调用 UniTour.setToken 把 token 保存到 localStorage 中，key 是 `unitour_token`。后续发送请求时，unitour-api.js 会从 localStorage 取出 token，并放到请求头中，格式是 `Authorization: Bearer <token>`。

请求进入 Controller 之前，会先经过 LoginCheckInterceptor 的 preHandle 方法。拦截器会从请求头中获取 Authorization，判断是否为空以及是否以 `Bearer ` 开头。如果不符合要求，就返回未登录。

如果格式正确，拦截器会截取出真正的 token，然后调用 JwtUtils.parseToken 解析 token。解析成功后会返回 Claims 对象，Claims 中包含 JWT 的载荷信息。后端通过 `claims.get("userId")` 取出 userId，再调用 `request.setAttribute("userId", userId)` 放入 request，后续 Controller 就可以通过 request 获取当前登录用户 ID。

即

```text
前端输入账号和密码，账号可以是用户名也可以是手机号
-> 前端调用 POST /api/v1/auth/login
-> AuthController#login 接收 LoginDTO
-> AuthServiceImpl#login 校验参数
-> UserMapper#selectByUsernameOrPhone 根据用户名或手机号查询用户
-> 如果用户不存在或状态异常，统一返回账号或密码错误
-> 调用 BCryptPasswordEncoder#matches 校验明文密码和数据库中的加密密码
-> 校验通过后，把 userId 和 username 放入 claims
-> 调用 JwtUtils#generateToken 生成 JWT
-> 封装 LoginVO 返回给前端
-> 前端通过 UniTour.setToken 把 token 保存到 localStorage
-> 后续请求由 unitour-api.js 自动携带 Authorization: Bearer <token>
-> 请求进入 Controller 前被 LoginCheckInterceptor#preHandle 拦截
-> 拦截器从 Authorization 请求头中截取 token
-> 调用 JwtUtils#parseToken 解析 token
-> 从 Claims 中取出 userId
-> request.setAttribute("userId", userId)
-> 后续 Controller 可以从 request 中获取当前登录用户 ID
```





### BCrypt 为什么不能重新加密后直接比较？

BCrypt 加密时会加入随机盐，所以同一个明文密码，每次加密出来的密文通常都不一样。

因此不能把用户输入的密码重新调用 encode 方法加密，然后和数据库中的密文做 equals 比较。因为重新生成的密文大概率和数据库中保存的密文不同。

正确做法是使用 `passwordEncoder.matches(明文密码, 数据库中的密文)`。matches 方法会从数据库密文中解析出盐值和算法参数，再用这些参数判断用户输入的明文密码是否匹配。



### 数据库为什么不能存明文密码？

数据库不能存明文密码，主要是为了安全。

如果数据库泄露，明文密码会直接暴露。很多用户可能在多个平台使用相同密码，这会导致风险扩散到其他系统。

所以项目中注册时会使用 BCrypt 对密码进行加密后再存入数据库，登录时再使用 matches 方法校验用户输入的明文密码和数据库中的密文是否匹配。



### token 过期后会发生什么？

项目中的 JWT 过期时间是 12 小时。

token 过期后，JwtUtils.parseToken 会解析失败并抛出异常。LoginCheckInterceptor 会捕获异常，返回统一的未登录结果，前端就需要重新登录来获取新的 token。



### 跨域预检请求为什么要放行？

LoginCheckInterceptor 中对 OPTIONS 请求直接放行，主要是为了兼容浏览器的跨域预检请求。

当前端发送一些非简单请求时，比如请求头中带有 Authorization，浏览器可能会先发送一个 OPTIONS 请求，询问后端这个请求是否允许发送。这个 OPTIONS 请求不是真正的业务请求，不应该要求登录。

如果拦截器把 OPTIONS 预检请求拦住，前端真正的业务请求可能还没发出去就失败了。所以这里直接对 OPTIONS 请求返回 true。



### 哪些接口被登录拦截器放行？

项目中拦截器默认拦截所有请求，然后在 WebConfig 中放行一部分路径。

认证相关接口会放行，比如注册、登录、忘记密码、注册验证码接口。高校公开浏览相关接口也会放行，比如高校列表、高校详情、校区 POI 列表。除此之外，前端静态页面和静态资源也会放行，比如首页、登录注册页、高校详情页、CSS、JS、图片等。

需要注意的是，静态页面放行不代表页面里的所有数据接口都放行。比如 user-center.html 页面本身可以打开，但页面中请求当前用户信息的 `/api/v1/users/me` 接口仍然需要登录，需要携带 JWT。

也就是说，页面访问和数据接口访问是两回事。静态页面只是 HTML、CSS、JS 资源，而用户中心数据接口会返回当前用户信息，必须依赖登录态。



### 为什么用 JWT？

JWT 可以让后端通过 token 识别用户身份，适合前后端分离项目。前端登录后保存 token，后续请求携带 token，后端解析后就能知道当前用户是谁。

JWT 的优点是使用方便，服务端不需要像 Session 那样保存每个用户的登录状态。但 JWT 一旦签发，在过期前不容易主动失效，所以实际项目中如果安全要求更高，可以结合 Redis 做 token 黑名单或刷新机制。



### JWT 和 Session 有什么区别？

Session 需要服务端保存用户登录状态，客户端通常只保存一个 sessionId；JWT 本身携带用户身份信息，服务端主要负责校验签名和解析内容。

在前后端分离项目中，JWT 使用起来比较方便，前端可以在请求头中携带 token。Session 更依赖服务端状态，如果是多台服务器部署，还需要考虑 Session 共享问题。

但是 JWT 也有缺点，比如 token 在过期前不容易主动失效，所以更完整的方案可以结合 Redis 黑名单、刷新 token 等机制。



### 注册验证码为什么用 Redis？

注册验证码属于临时数据，只需要短时间有效，不适合存到 MySQL 这种持久化数据库里。所以我使用 Redis 来存储验证码。

后端生成验证码时，会同时生成一个 captchaId，并把验证码 code 以 captchaId 作为标识存入 Redis，设置 300 秒过期时间。前端注册时提交 captchaId 和用户输入的验证码，后端根据 captchaId 从 Redis 中取出真实验证码进行比对。

如果校验成功，就删除 Redis 中的验证码，避免同一个验证码被重复使用。如果验证码过期，Redis 会自动删除，用户就需要重新获取验证码。

调用链：请求验证码 -> 生成 captchaId 和 code -> 写入 Redis 并设置 TTL -> 注册时提交 captchaId 和 code -> 从 Redis 查询并比对 -> 成功后删除验证码 -> 写入用户。

关键代码位置：AuthController、AuthServiceImpl、RedisKeyConstants、CaptchaVO。



### 为什么不用 MySQL 存验证码？

验证码是短生命周期数据，只用于一次注册校验，用完或者过期就应该失效。放 MySQL 会产生很多无意义的临时数据，还需要额外清理。

Redis 支持 TTL，天然适合这种临时数据。验证码过期后 Redis 可以自动删除，业务上也更轻量。



### 注册成功后为什么要删除验证码？

注册成功后删除验证码是为了防止同一个验证码被重复使用。

虽然验证码本身设置了过期时间，但如果用户在过期时间内重复提交请求，仍然可能造成验证码被多次使用。所以校验成功后主动删除，可以让验证码只使用一次。



### 高校详情缓存怎么实现？

高校详情页属于读多写少的数据，比如高校基础信息、校区信息、评分汇总等，不会频繁变化，但可能被多次访问，所以我对高校详情做了 Redis 缓存。

查询高校详情时，Service 层会先根据 universityId 拼接 Redis key，然后先查 Redis。如果 Redis 中存在缓存，就直接反序列化后返回。如果没有命中缓存，再查询 MySQL，组装高校详情数据，然后写入 Redis，并设置过期时间。

当用户发布或删除主评价后，因为高校评分信息可能发生变化，所以会删除对应高校详情缓存。这样下次查询时会重新从 MySQL 加载最新数据，再写入 Redis。

调用链：查询高校详情 -> 拼接 Redis key -> 先查 Redis -> 命中则直接返回 -> 未命中查 MySQL -> 组装高校详情和校区列表、评分信息 -> 写入 Redis -> 返回前端。

关键代码位置：UniversityController、UniversityServiceImpl、UniversityMapper、CampusMapper、RedisKeyConstants。

注意：当前项目主要是在发布和删除主评价后删除高校详情缓存，不要夸大成所有评价互动都做了完整缓存一致性。



### 为什么高校详情适合加缓存？

高校详情是典型的读多写少数据。用户可能频繁查看学校详情，但高校基础信息、校区信息不会频繁变化。

如果每次详情查询都直接查 MySQL，就会重复执行高校基础信息查询、校区列表查询和评分聚合查询。加 Redis 缓存后，后续相同高校详情可以优先从 Redis 读取，减少数据库压力，提高接口响应速度。



### 为什么缓存要设置过期时间？

设置过期时间可以避免缓存长期不更新，也能防止 Redis 中堆积太多历史数据。

即使某些场景没有主动删除缓存，过期时间也能起到兜底作用。等缓存过期后，下次查询会重新从 MySQL 加载最新数据。



### 缓存和数据库不一致怎么办？

当前项目采用的是 Cache Aside 思路，也就是查询时先查缓存，缓存未命中再查数据库并写入缓存；数据发生变化时，先更新数据库，再删除对应缓存。

对于 UniTour 当前的项目规模来说，这种方式已经够用。比如发布或删除主评价后，评分汇总可能变化，所以会删除对应高校详情缓存，让下次查询重新加载。

如果是更高并发、更高一致性要求的业务，可以进一步考虑延迟双删、消息队列重试、缓存更新日志等方式。



### 评价发布流程怎么实现？

评价发布不是简单插入一条评论，我在 Service 层做了多层业务校验。

首先需要判断用户是否登录，然后校验用户资料是否完善。接着校验高校是否存在，如果用户选择了校区，还要校验这个校区是否属于当前高校。然后校验评价内容长度，以及多维评分字段是否完整。

如果评分字段都填写了，就根据多个维度计算综合评分。校验通过后，将评价数据写入 university_review 表。由于新增评价可能影响高校详情页中的评分汇总，所以发布成功后会删除对应高校详情缓存，让下次查询重新加载最新数据。

调用链：发布评价 -> 获取当前 userId -> 校验用户资料 -> 校验高校存在 -> 校验校区归属 -> 校验内容和评分 -> 计算综合评分 -> 写入 university_review -> 删除高校详情缓存。

关键代码位置：ReviewController、ReviewServiceImpl、ReviewMapper、UserMapper、UniversityMapper、RedisKeyConstants。



### 为什么要校验校区是否属于高校？

校验校区归属是为了保证数据关系正确。

如果不校验，前端传错参数或者有人恶意构造请求，就可能出现给 A 高校发布评价，却绑定到 B 高校校区的情况，导致评价数据和校区数据关系混乱。



### 为什么评分要么全填要么全不填？

因为项目中的评分是多维度评分。如果只填写一部分维度，后续计算综合评分和展示评分时会出现数据不完整的问题。

所以我在发布评价时要求评分字段要么都填写，要么都不填写。这样可以保证评分数据的一致性，也方便后续做平均分聚合。



### 点赞怎么防止重复点赞？

点赞功能除了在业务层判断用户是否已经点赞，还在数据库层做了唯一约束。

review_like 表中可以对 review_id 和 user_id 建联合唯一索引，表示同一个用户对同一条评价只能点赞一次。这样即使出现并发请求，数据库层也能兜底防止重复点赞。

业务层负责正常判断和返回提示，数据库唯一索引负责保证数据最终不重复。项目中插入点赞关系时也可以配合 INSERT IGNORE，避免重复插入导致数据异常。

关键代码位置：ReviewController、ReviewServiceImpl、ReviewMapper、ReviewMapper.xml。



### 回复功能怎么实现？

回复功能主要是围绕评价展开的。用户登录后可以对某条评价进行回复，后端会先校验用户身份，再校验评价是否存在，然后把回复内容写入 review_reply 表。

查询评价列表时，除了查询评价本身，还会根据评价 ID 查询对应的回复数据，并组装到返回结果中。这样前端展示评价列表时，可以同时展示评价下的回复内容。

如果数据量继续增大，后续可以把回复也做分页，或者评价列表中只展示部分回复，点击后再加载完整回复列表。



### 数据库表怎么设计？

项目主要有用户、高校、校区、POI、评价、点赞、回复这些核心表。

users 表存储用户账号、密码、手机号、头像、资料完善状态等信息。university 表存储高校基础信息。campus 表存储校区信息，并通过 university_id 关联高校。poi 表存储校园地点，比如食堂、宿舍、教学楼等，也会关联到高校和校区。

university_review 表存储用户对高校的评价和多维评分。review_like 表存储用户对评价的点赞关系。review_reply 表存储评价下的回复内容。

这些表之间主要通过主键 ID 和关联字段进行连接，比如 campus 通过 university_id 关联 university，review 通过 university_id 和 user_id 关联高校和用户，review_reply 通过 review_id 关联评价。



### 你的索引怎么设计？

索引主要围绕高频查询和数据约束来设计。

评价列表经常根据 university_id 查询某个高校下的评价，所以 university_review 表适合在 university_id 上建立索引。回复经常根据 review_id 查询，所以 review_reply 表适合在 review_id 上建索引。

点赞表需要防止重复点赞，所以 review_like 表适合对 review_id 和 user_id 建联合唯一索引。这个索引既能提升按照评价查询点赞关系的效率，也能从数据库层面保证同一个用户不能重复点赞同一条评价。

回答时可以结合 MySQL 索引原则：高频查询字段、关联字段、排序字段、唯一性约束字段适合建索引，但索引不是越多越好，因为写操作时也要维护索引。



### Redis 在项目中具体用在哪里？

Redis 在项目中主要有两个使用场景。

第一个是注册验证码。验证码是临时数据，需要短时间有效，所以用 Redis 存储，并设置过期时间。

第二个是高校详情缓存。高校详情是读多写少的数据，查询时先查 Redis，缓存未命中再查 MySQL，查询结果写入 Redis。发布或删除主评价后，会删除对应高校详情缓存，保证下次查询时重新加载最新数据。

这两个场景分别对应 Redis 的临时数据存储和缓存加速能力。



### OSS 文件上传怎么实现？

项目中的图片没有直接存到数据库，而是上传到阿里云 OSS。

前端选择图片后，通过上传接口把文件传给后端。后端接收 MultipartFile，校验文件后生成唯一文件名，然后调用 OSS SDK 上传文件。上传成功后，OSS 会返回文件访问地址，后端把这个 URL 返回给前端，数据库中只保存 URL。

这样做可以避免把大文件直接存入数据库，减轻数据库压力，也方便前端直接通过 URL 展示图片。

关键代码位置：UserController、CampusController、PoiController、OssUploadService、OssUploadServiceImpl、OssProperties。



### 为什么不把图片存数据库？

图片属于大文件，直接存数据库会增加数据库压力，也不利于访问和扩展。

更常见的做法是文件存对象存储，数据库只保存访问地址。这样数据库只负责结构化数据，OSS 负责文件存储和访问。



### 统一返回结果怎么做？

项目中使用统一的 Result 返回结构，接口返回的数据格式保持一致。

正常情况下返回成功状态、提示信息和数据；异常情况下返回失败状态和错误信息。这样前端处理接口响应时会更统一，不需要每个接口单独适配不同格式。

关键代码位置：Result、PageResult、GlobalExceptionHandler。



### 项目中异常怎么处理？

项目中不是在每个 Controller 里都写 try-catch，而是通过全局异常处理器统一处理异常。

业务代码中如果出现异常，可以向上抛出，最后由全局异常处理器捕获，并转换成统一的 Result 返回给前端。这样可以减少重复代码，也能保证接口错误返回格式一致。

当前项目中异常处理还比较基础，主要是统一捕获运行时异常。后续可以进一步抽象业务异常类和错误码，比如 BusinessException 和 ErrorCode，让异常语义更清晰。



### 这个项目的亮点是什么？

我觉得这个项目主要有三个亮点。

第一，它不是单纯的 CRUD，而是围绕择校场景做了高校、校区、POI、评价、评分这些业务建模，评价发布时也做了用户状态、高校存在、校区归属、评分完整性等业务校验。

第二，Redis 不是为了堆技术栈，而是用在了两个比较自然的业务场景里，一个是注册验证码，一个是高校详情缓存。

第三，项目从数据库设计、接口开发、前端页面展示、OSS 文件上传、Redis 缓存到服务器部署形成了完整闭环，不只是本地写了几个接口。



### 项目有什么不足？

这个项目目前还有一些不足。

第一，权限体系还比较基础，目前主要是普通用户登录认证，还没有做更细粒度的角色权限控制。

第二，缓存一致性策略比较简单，主要是通过更新数据库后删除缓存来保证高校详情数据更新。后续如果并发更高，可以考虑延迟双删、消息队列等方式优化。

第三，异常处理目前是基础版本，后续可以抽象统一的业务异常类和错误码。

第四，搜索能力目前还比较基础，如果后续数据量更大，可以考虑引入 Elasticsearch 或者更完善的筛选排序机制。



### 这个项目难点在哪里？

对我来说，比较有挑战的地方主要有两个。

第一个是把业务关系设计清楚。比如高校、校区、POI、评价、点赞、回复之间不是孤立的，需要在数据库表结构和接口返回结构上保持清晰关系。

第二个是把 Redis、JWT、OSS 这些技术真正接入业务流程，而不是只停留在单独 demo。比如 JWT 和拦截器结合实现登录态校验，Redis 用于验证码和高校详情缓存，OSS 用于图片上传。

这些东西单独看都不算特别复杂，但把它们串成一个能正式跑通的项目，对我来说是这个项目的主要收获。



### 如果面试官问：这个项目是不是太简单？

这个项目不是一个复杂的大型系统，我对它的定位是一个面向实习阶段的完整后端项目。

它的重点不是高并发或者复杂架构，而是把 Java 后端开发中常见的能力串起来，包括接口设计、数据库表设计、MyBatis、Redis、JWT、OSS、统一返回、异常处理和部署。

我觉得它目前能体现我具备基础后端开发能力，但如果继续优化，后面可以在权限体系、缓存一致性、搜索能力、日志监控、接口测试这些方面继续加强。
