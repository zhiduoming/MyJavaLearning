# MySQL

## 基础与存储引擎

### MySQL 常见存储引擎有哪些？

常见的存储引擎主要有InnoDB、MyISAM、Memory、Archive

实际开发中最常用的是 InnoDB，也是 MySQL5.5 之后的默认存储引擎。

InnoDB 支持事务、外键、行级锁和崩溃恢复，适合大多数业务系统。

MyISAM 是早期常用的存储引擎，不支持事务和行级锁，主要使用表级锁。

Memory 存储引擎把数据放在内存当中，访问速度极快但数据容易丢失。

Archive /ˈɑːrkaɪv/主要用于归档场景。



### InnoDB 和 MyISAM 的区别？

InnoDB 和 MyISAM 都是 MySQL 中常见的存储引擎，其中InnoDB 引擎是 MySQL5.5 之后的默认存储引擎。

InnoDB 引擎支持事务、支持外键、支持行级锁、支持 MVCC、崩溃恢复能力强。适合高并发和对数据一致性要求较高的场景。

MyISAM 引擎不支持事务、不支持外键、不支持行级锁，支持表级锁、崩溃恢复能力弱。在一些对事务要求不高或者读多写少的简单场景下查询可能较快。

在索引结构上，InnoDB 的主键索引是聚集索引，叶子节点存放整行数据；而 MyISAM 的索引和数据是分开的，叶子节点只存放数据文件地址。

在实际开发中主要使用 InnoDB 引擎。



### 为什么现在更推荐使用 InnoDB？

因为 InnoDB 引擎是 MySQL5.5 之后的默认存储引擎，它支持事务、支持外键、支持行级锁、支持 MVCC、崩溃恢复能力强，适合高并发和对数据一致性要求较高的场景，比如用户、订单、点赞、评论这些核心业务数据。所以实际开发中主要使用 InnoDB。



### 一条 SQL 查询语句的执行流程大概是什么？

一条 SQL 查询语句大致会经过连接器、查询缓存、分析器、优化器、执行器和存储引擎几个阶段。

首先客户端与 MySQL 建立连接，连接器负责身份认证、权限校验和连接管理。

然后老版本 MySQL 会先查询缓存，如果命中可以直接返回结果，但 MySQL 8.0 已经移除了查询缓存。

接着分析器会对 SQL 进行词法分析和语法分析，判断 SQL 的语法是否正确。

然后优化器会根据索引、统计信息等选择执行计划，比如决定使用哪个索引、表的连接顺序等。

最后执行器按照执行计划调用存储引擎接口，由存储引擎真正读取数据，并将结果返回给客户端。



## 索引

### 索引是什么？

索引帮助 MySQL 用来快速查询数据的一种数据结构，相当于数据库的目录。

如果没有索引的话，MySQL 需要从头到尾扫描整张表；有了索引之后可以通过索引快速定位到满足条件的数据，减少扫描的数据量，从而提高查询速度。

但是索引也有代价，它本身是一种数据结构，会占用额外的空间，并且在插入、删除、更新数据的时候、数据库还要维护索引，所以索引并不是越多越好。



### 索引有什么优缺点？

索引的优点主要是可以提高查询效率。如果没有索引，MySQL 就需要从头到尾扫描整张表，有了索引就可以根据索引快速定位数据，减少扫描行数，从而提高查询速度。索引还可以提高排序查询、分组查询、范围查询的效率。而且唯一索引可以保证字段唯一。

缺点是索引会占用额外的存储空间，而且插入、删除、更新数据需要维护索引结构，会降低写操作频率。索引不是越多越好，索引过多会增加维护成本。在区分度高，查询频繁，经常需要使用 where、join、order by、group by 的字段上使用索引效果更好。



### MySQL 索引为什么使用 B+ 树？

MySQL 索引使用 B+树主要是因为 B+树可以减少磁盘 IO 次数且支持范围查询。

首先，数据库往往数据量很大，影响查询性能最关键的因素就是磁盘 IO 次数，B+树是多路平衡树，其一个节点往往可以存放多个 key 和多个子节点，树往往很矮，磁盘 IO 的次数少，所以查询速度很快。

其次，B+树的非叶子节点通常只存放索引和指针，不存放完整数据，因此一个节点可以存放更多的索引，从而进一步降低了树高。

另外，B+树的数据全部存放在叶子节点，查询稳定性更高，而且叶子节点之间使用链表连接起来，并且是有序的，所以非常适合范围查询和排序的场景。

相比于普通二叉树和红黑树，B+树的树高更低，磁盘 IO 的次数更少，查询速度更快。相比于 B 树，叶子节点之间使用链表连接，范围查询效果非常好，而且非叶子节点能存放更多的索引。



### B 树和 B+ 树有什么区别？

B 树和 B+树都是多路平衡树，B+树相比于 B 树，其非叶子节点不存放数据，只存放索引和指针，从而每个节点存放的索引更多，进一步降低了树高。 B+树的数据都存放在叶子节点中，叶子节点之间还使用链表进行连接，从而比 B 树更支持范围查询，查询的稳定性更高。

所以 B+树结构更适合作为MySQL 索引

### 聚簇索引和非聚簇索引的区别？

聚簇索引和非聚簇索引的区别主要是叶子节点存放的内容不同。

在 InnoDB 中，主键索引就是聚簇索引，它的叶子节点中存放完整数据，所以通过主键查询的时候，找到叶子节点就可以查询到整行的数据。

非聚簇索引也叫二级索引，比如普通索引，联合索引等。InnoDB 中二级索引的叶子节点中存放的是对应的主键值，而不是完整的行数据。先通过二级索引先查询到主键值，再根据主键值回到聚簇索引中查询到完整的行数据，这个过程就叫回表。

一张 InnoDB 表只有一个聚簇索引，因为数据只能按一种方式组织，但可以有多个非聚簇索引。一般如果表有主键，InnoDB 会使用主键作为聚簇索引。

### 什么是回表？

回表是指根据二级索引查询数据时，需要的字段不在二级索引中，就先查询到对应的主键，然后根据主键回到聚簇索引中查询到整行数据的过程，如果在二级索引中能查到需要的字段，就不需要回表，这就叫覆盖索引。

### 什么是覆盖索引？

覆盖索引是指查询需要的字段都可以从索引中直接获取，不需要再回到聚簇索引查询完整行数据。

它不是一种单独的索引类型，而是一种查询效果。

### 什么是联合索引？

联合索引是指在多个字段上一起建立的索引，比如给用户表的姓名和年龄建立（name，age）联合索引，它不是两个单独的索引，而是根据字段顺序组织的索引，查询时会先根据 name 进行排序，name 相同的情况下再按照 age 排序。

联合索引最重要的是最左前缀原则，也就是说查询条件要从最左边的字段开始，并且尽可能保持连续，才能更好地利用索引。联合索引可以提高条件查询的效率，也可能形成覆盖索引，减少回表。

### 什么是最左前缀原则？

使用联合索引时，查询条件从最左边的字段开始，并且尽可能地保持连续，才能更好地利用索引。

### 索引失效有哪些常见场景？

第一，对索引列进行函数或者计算，可能导致MySQL无法直接利用索引的有序结构。

第二，使用 like 的时候用 % 开头，这样无法确定索引扫描的起点。

第三，发生隐式类型转换，比如字段是字符串类型，但是查询的时候没有加引号，可能导致索引失效。

第四，使用联合索引时不满足最左前缀原则。

第五，使用`!=`、`not in`、`not like` 或者`or`使用不当或者查询字段区分度很低，返回的数据量太大时，优化器可能也不走索引。

总的来说，索引是否生效要看 SQL 写法、索引结构、字段区分度和优化器成本判断，不能只看字段有没有建索引。

### 索引是不是越多越好？

索引不是越多越好，索引本身也是一种数据结构，它会占用存储空间，而且插入、删除、更新数据都需要维护索引结构，会降低写操作的效率。

另外，索引过多也会增加优化器选择执行计划的成本，低区分度字段建索引收益也不高。

### 什么字段适合建立索引，什么字段不适合建索引？

需要频繁查询、区分度高、经常用于过滤、排序、分组和连接的字段更适合建立索引。

如果多个字段经常放在一起作为查询条件，则可以考虑建立联合索引，但要注意要遵循最左前缀原则。

更新频繁、区分度低，很少用于查询条件的字段不适合建立索引。



### 什么是 SQL 提示？

SQL 提示是指在 SQL 语句中给数据库优化器添加一些提示，用来影响它选择的执行计划。MySQL 中常见的是索引提示，比如`USE INDEX`,  `IGNORE INDEX`,  `FORCE INDEX`。

其中`USE INDEX`是指建议优化器使用某个索引，`IGNORE INDEX`是让优化器忽略某个索引，`FORCE INDEX`是指强制地使优化器使用某个索引。

一般会先通过`explain`来查看 SQL 的执行计划，如果发现优化器没有选择合适的索引，再考虑使用 SQL 提示。SQL 提示需要谨慎使用，因为数据分布和索引情况发生变化后，强制指定索引可能引起性能下降。



### 什么是前缀索引？

前缀索引是指对字符串字段的前一部分字符建立索引，而不是对整个字段建立索引。比如对 email 字段建立 email(10) 索引，就是只取前 10 个字符作为索引。

前缀索引主要用于较长的字符串字段，可以减少索引占用空间和维护成本。但前缀长度要选择合适，如果太短，区分度不够，索引效果不好；如果太长，又接近完整索引，节省空间不明显。

前缀索引的缺点是通常不能很好支持覆盖索引，因为索引里只保存字段前缀，不保存完整字段；另外对完整字段排序的支持也有限。

所以前缀索引适合长字符串字段，并且字段前缀区分度较高的场景。



## 事务与隔离级别

### 什么是事务？

事务是数据库中一组操作的逻辑执行单元，这组操作要么全部成功，要么全部失败，主要用来保证数据的一致性。

如果在事务的一组操作中发生了异常，则会进行事务回滚的操作，从而保证这组操作的异常不会影响到原数据。

### 事务的 ACID 特性是什么？

原子性、一致性、隔离性、持久性。

原子性（Atomicity） 是指事务是不可分割的最小单位，要么同时成功，要么同时失败。

一致性（consistency）是指事务完成前后，必须使所有数据保持一致，比如转账操作完成后，两个人总资金是不变的。

隔离性（Isolation） 是指多个事务并发执行的时候，互不干扰，保持相互独立。

持久性（Durability）是指，事务一旦提交或者回滚，它对数据库中的数据的修改是永久的，即使系统崩溃，也能够恢复。



### MySQL 事务隔离级别有哪些？

MySQL 中事务的隔离级别主要有 4 种，从低到高分别是读未提交、读已提交、可重复读、串行化

读未提交允许一个事务读到其他事务还未提交的数据，可能会出现脏读、不可重复读、幻读

读已提交只能读到其他事务已经提交的数据，可以避免脏读，但是可能会出现不可重复读、幻读。

可重复读可以保证同一个事务多次读取同一条记录结果保持一致，可以避免脏读和不可重复读，MySQL 中 InnoDB 引擎默认的隔离级别就是可重复读，理论上来说还是有可能出现幻读，但是 InnoDB 通过 MVCC、Next-key Lock 等机制可以在很多场景避免幻读。

串行化隔离级别最高，可以避免脏读、不可重复读、幻读。但是其并发性能最差，实际业务中很少使用。

### 什么是脏读、不可重复读、幻读？

脏读、不可重复读、幻读都是在并发场景下产生的经典问题。

脏读是指一个事务读到了其他事务还没有提交的数据。如果对方回滚，则查到的这条记录是无效的。

不可重复读是指，在同一个事务中，多次读取同一条记录读到的结果不一致。通常是因为其他事务对该记录进行了修改。

幻读是指在同一个事务中，多次相同的范围查询操作得到的结果集数量不同，通常是因为其他事务进行了插入或者删除了符合条件的记录。

### 不同隔离级别分别解决了哪些问题？

读未提交隔离级别最低，一个事务可以读到其他事务未提交的数据，可能出现脏读、不可重复读和幻读。

读已提交解决了脏读，但是无法避免不可重复读和幻读。

可重复读解决了脏读和不可重复读，但理论上还是可能出现幻读，是 MySQL InnoDB默认的隔离级别。

串行化的隔离级别最高，完全避免了脏读、不可重复读和幻读，但是它的并发性能最差，实际开发中很少使用。

### MySQL InnoDB 默认隔离级别是什么？

MySQL 中默认的隔离级别是可重复读，其避免了脏读、不可重复读，理论上还是可能出现幻读，但是由于 InnoDB 的 MVCC、next-key Lock 等机制使得在很多场景下可以避免幻读。

### 为什么 MySQL 默认使用可重复读？

因为读未提交、读已提交的隔离级别太低，读未提交会出现脏读、不可重复读、幻读的问题，读已提交会出现不可重复读和幻读的问题，并发场景下的安全性太低。

串行化的隔离级别虽然最高可以避免脏读、不可重复读、幻读，但是它的并发性能太差了，所以一般很少使用。

而可重复读可以避免脏读和不可重复读，而且由于 InnoDB 的 MVCC、next - key Lock 等机制可以在很多场景下避免幻读，是并发安全和并发性能的平衡。

### 事务一般用在什么场景？

事务一般用于多个数据库操作之间需要保持一致性的场景，需要保证保证多个操作要么同时成功，要么同时失败，出现异常会回滚，不会影响到原数据。通常用于对多个表进行修改，多步骤写操作、核心业务状态变更的场景。
