# MySQL面试

## 基础与存储引擎

### MySQL 常见存储引擎有哪些？

常见的存储引擎主要有InnoDB、MyISAM、Memory、Archive

实际开发中最常用的是 InnoDB，也是 MySQL5.5 之后的默认存储引擎。

InnoDB 支持事务、外键、行级锁和崩溃恢复，适合大多数业务系统。

MyISAM 是早期常用的存储引擎，不支持事务和行级锁，主要使用表级锁。

Memory 存储引擎把数据放在内存当中，访问速度极快但数据容易丢失。

Archive /ˈɑːrkaɪv/主要用于归档场景。



### InnoDB 和 MyISAM 的区别？

InnoDB 和 MyISAM 都是 MySQL 中常见的存储引擎，其中InnoDB 引擎是 MySQL5.5 之后的默认存储引擎。

InnoDB 引擎支持事务、支持外键、支持行级锁、支持 MVCC、崩溃恢复能力强。适合高并发和对数据一致性要求较高的场景。

MyISAM 引擎不支持事务、不支持外键、不支持行级锁，支持表级锁、崩溃恢复能力弱。在一些对事务要求不高或者读多写少的简单场景下查询可能较快。

在索引结构上，InnoDB 的主键索引是聚集索引，叶子节点存放整行数据；而 MyISAM 的索引和数据是分开的，叶子节点只存放数据文件地址。

在实际开发中主要使用 InnoDB 引擎。



### 为什么现在更推荐使用 InnoDB？

因为 InnoDB 引擎是 MySQL5.5 之后的默认存储引擎，它支持事务、支持外键、支持行级锁、支持 MVCC、崩溃恢复能力强，适合高并发和对数据一致性要求较高的场景，比如用户、订单、点赞、评论这些核心业务数据。所以实际开发中主要使用 InnoDB。



### 一条 SQL 查询语句的执行流程大概是什么？

一条 SQL 查询语句大致会经过连接器、查询缓存、分析器、优化器、执行器和存储引擎几个阶段。

首先客户端与 MySQL 建立连接，连接器负责身份认证、权限校验和连接管理。

然后老版本 MySQL 会先查询缓存，如果命中可以直接返回结果，但 MySQL 8.0 已经移除了查询缓存。

接着分析器会对 SQL 进行词法分析和语法分析，判断 SQL 的语法是否正确。

然后优化器会根据索引、统计信息等选择执行计划，比如决定使用哪个索引、表的连接顺序等。

最后执行器按照执行计划调用存储引擎接口，由存储引擎真正读取数据，并将结果返回给客户端。



## 索引

### 索引是什么？

索引帮助 MySQL 用来快速查询数据的一种数据结构，相当于数据库的目录。

如果没有索引的话，MySQL 需要从头到尾扫描整张表；有了索引之后可以通过索引快速定位到满足条件的数据，减少扫描的数据量，从而提高查询速度。

但是索引也有代价，它本身是一种数据结构，会占用额外的空间，并且在插入、删除、更新数据的时候、数据库还要维护索引，所以索引并不是越多越好。



### 索引有什么优缺点？

索引的优点主要是可以提高查询效率。如果没有索引，MySQL 就需要从头到尾扫描整张表，有了索引就可以根据索引快速定位数据，减少扫描行数，从而提高查询速度。索引还可以提高排序查询、分组查询、范围查询的效率。而且唯一索引可以保证字段唯一。

缺点是索引会占用额外的存储空间，而且插入、删除、更新数据需要维护索引结构，会降低写操作频率。索引不是越多越好，索引过多会增加维护成本。在区分度高，查询频繁，经常需要使用 where、join、order by、group by 的字段上使用索引效果更好。



### MySQL 索引为什么使用 B+ 树？

MySQL 索引使用 B+树主要是因为 B+树可以减少磁盘 IO 次数且支持范围查询。

首先，数据库往往数据量很大，影响查询性能最关键的因素就是磁盘 IO 次数，B+树是多路平衡树，其一个节点往往可以存放多个 key 和多个子节点，树往往很矮，磁盘 IO 的次数少，所以查询速度很快。

其次，B+树的非叶子节点通常只存放索引和指针，不存放完整数据，因此一个节点可以存放更多的索引，从而进一步降低了树高。

另外，B+树的数据全部存放在叶子节点，查询稳定性更高，而且叶子节点之间使用链表连接起来，并且是有序的，所以非常适合范围查询和排序的场景。

相比于普通二叉树和红黑树，B+树的树高更低，磁盘 IO 的次数更少，查询速度更快。相比于 B 树，叶子节点之间使用链表连接，范围查询效果非常好，而且非叶子节点能存放更多的索引。



### B 树和 B+ 树有什么区别？

B 树和 B+树都是多路平衡树，B+树相比于 B 树，其非叶子节点不存放数据，只存放索引和指针，从而每个节点存放的索引更多，进一步降低了树高。 B+树的数据都存放在叶子节点中，叶子节点之间还使用链表进行连接，从而比 B 树更支持范围查询，查询的稳定性更高。

所以 B+树结构更适合作为MySQL 索引

### 聚簇索引和非聚簇索引的区别？

聚簇索引和非聚簇索引的区别主要是叶子节点存放的内容不同。

在 InnoDB 中，主键索引就是聚簇索引，它的叶子节点中存放完整数据，所以通过主键查询的时候，找到叶子节点就可以查询到整行的数据。

非聚簇索引也叫二级索引，比如普通索引，联合索引等。InnoDB 中二级索引的叶子节点中存放的是对应的主键值，而不是完整的行数据。先通过二级索引查询到主键值，再根据主键值回到聚簇索引中查询到完整的行数据，这个过程就叫回表。

一张 InnoDB 表只有一个聚簇索引，因为数据只能按一种方式组织，但可以有多个非聚簇索引。一般如果表有主键，InnoDB 会使用主键作为聚簇索引。

### 什么是回表？

回表是指根据二级索引查询数据时，需要的字段不在二级索引中，就先查询到对应的主键，然后根据主键回到聚簇索引中查询到整行数据的过程，如果在二级索引中能查到需要的字段，就不需要回表，这就叫覆盖索引。

### 什么是覆盖索引？

覆盖索引是指查询需要的字段都可以从索引中直接获取，不需要再回到聚簇索引查询完整行数据。

它不是一种单独的索引类型，而是一种查询效果。

### 什么是联合索引？

联合索引是指在多个字段上一起建立的索引，比如给用户表的姓名和年龄建立（name，age）联合索引，它不是两个单独的索引，而是根据字段顺序组织的索引，查询时会先根据 name 进行排序，name 相同的情况下再按照 age 排序。

联合索引最重要的是最左前缀原则，也就是说查询条件要从最左边的字段开始，并且尽可能保持连续，才能更好地利用索引。联合索引可以提高条件查询的效率，也可能形成覆盖索引，减少回表。

### 什么是最左前缀原则？

使用联合索引时，查询条件从最左边的字段开始，并且尽可能地保持连续，才能更好地利用索引。

### 索引失效有哪些常见场景？

第一，对索引列进行函数或者计算，可能导致MySQL无法直接利用索引的有序结构。

第二，使用 like 的时候用 % 开头，这样无法确定索引扫描的起点。

第三，发生隐式类型转换，比如字段是字符串类型，但是查询的时候没有加引号，可能导致索引失效。

第四，使用联合索引时不满足最左前缀原则。

第五，使用`!=`、`not in`、`not like` 或者`or`使用不当或者查询字段区分度很低，返回的数据量太大时，优化器可能也不走索引。

总的来说，索引是否生效要看 SQL 写法、索引结构、字段区分度和优化器成本判断，不能只看字段有没有建索引。

### 索引是不是越多越好？

索引不是越多越好，索引本身也是一种数据结构，它会占用存储空间，而且插入、删除、更新数据都需要维护索引结构，会降低写操作的效率。

另外，索引过多也会增加优化器选择执行计划的成本，低区分度字段建索引收益也不高。

### 什么字段适合建立索引，什么字段不适合建索引？

需要频繁查询、区分度高、经常用于过滤、排序、分组和连接的字段更适合建立索引。

如果多个字段经常放在一起作为查询条件，则可以考虑建立联合索引，但要注意要遵循最左前缀原则。

更新频繁、区分度低，很少用于查询条件的字段不适合建立索引。



### 什么是 SQL 提示？

SQL 提示是指在 SQL 语句中给数据库优化器添加一些提示，用来影响它选择的执行计划。MySQL 中常见的是索引提示，比如`USE INDEX`,  `IGNORE INDEX`,  `FORCE INDEX`。

其中`USE INDEX`是指建议优化器使用某个索引，`IGNORE INDEX`是让优化器忽略某个索引，`FORCE INDEX`是指强制地使优化器使用某个索引。

一般会先通过`explain`来查看 SQL 的执行计划，如果发现优化器没有选择合适的索引，再考虑使用 SQL 提示。SQL 提示需要谨慎使用，因为数据分布和索引情况发生变化后，强制指定索引可能引起性能下降。



### 什么是前缀索引？

前缀索引是指对字符串字段的前一部分字符建立索引，而不是对整个字段建立索引。比如对 email 字段建立 email(10) 索引，就是只取前 10 个字符作为索引。

前缀索引主要用于较长的字符串字段，可以减少索引占用空间和维护成本。但前缀长度要选择合适，如果太短，区分度不够，索引效果不好；如果太长，又接近完整索引，节省空间不明显。

前缀索引的缺点是通常不能很好支持覆盖索引，因为索引里只保存字段前缀，不保存完整字段；另外对完整字段排序的支持也有限。

所以前缀索引适合长字符串字段，并且字段前缀区分度较高的场景。



## 事务与隔离级别

### 什么是事务？

事务是数据库中一组操作的逻辑执行单元，这组操作要么全部成功，要么全部失败，主要用来保证数据的一致性。

如果在事务的一组操作中发生了异常，则会进行事务回滚的操作，从而保证这组操作的异常不会影响到原数据。

### 事务的 ACID 特性是什么？

原子性、一致性、隔离性、持久性。

原子性（Atomicity） 是指事务是不可分割的最小单位，要么同时成功，要么同时失败。

一致性（consistency）是指事务完成前后，必须使所有数据保持一致，比如转账操作完成后，两个人总资金是不变的。

隔离性（Isolation） 是指多个事务并发执行的时候，互不干扰，保持相互独立。

持久性（Durability）是指，事务一旦提交或者回滚，它对数据库中的数据的修改是永久的，即使系统崩溃，也能够恢复。



### MySQL 事务隔离级别有哪些？

MySQL 中事务的隔离级别主要有 4 种，从低到高分别是读未提交、读已提交、可重复读、串行化

读未提交允许一个事务读到其他事务还未提交的数据，可能会出现脏读、不可重复读、幻读

读已提交只能读到其他事务已经提交的数据，可以避免脏读，但是可能会出现不可重复读、幻读。

可重复读可以保证同一个事务多次读取同一条记录结果保持一致，可以避免脏读和不可重复读，MySQL 中 InnoDB 引擎默认的隔离级别就是可重复读，理论上来说还是有可能出现幻读，但是 InnoDB 通过 MVCC、Next-key Lock 等机制可以在很多场景避免幻读。

串行化隔离级别最高，可以避免脏读、不可重复读、幻读。但是其并发性能最差，实际业务中很少使用。

### 什么是脏读、不可重复读、幻读？

脏读、不可重复读、幻读都是在并发场景下产生的经典问题。

脏读是指一个事务读到了其他事务还没有提交的数据。如果对方回滚，则查到的这条记录是无效的。

不可重复读是指，在同一个事务中，多次读取同一条记录读到的结果不一致。通常是因为其他事务对该记录进行了修改。

幻读是指在同一个事务中，多次相同的范围查询操作得到的结果集数量不同，通常是因为其他事务进行了插入或者删除了符合条件的记录。

### 不同隔离级别分别解决了哪些问题？

读未提交隔离级别最低，一个事务可以读到其他事务未提交的数据，可能出现脏读、不可重复读和幻读。

读已提交解决了脏读，但是无法避免不可重复读和幻读。

可重复读解决了脏读和不可重复读，但理论上还是可能出现幻读，是 MySQL InnoDB默认的隔离级别。

串行化的隔离级别最高，完全避免了脏读、不可重复读和幻读，但是它的并发性能最差，实际开发中很少使用。

### MySQL InnoDB 默认隔离级别是什么？

MySQL 中默认的隔离级别是可重复读，其避免了脏读、不可重复读，理论上还是可能出现幻读，但是由于 InnoDB 的 MVCC、next-key Lock 等机制使得在很多场景下可以避免幻读。

### 为什么 MySQL 默认使用可重复读？

因为读未提交、读已提交的隔离级别太低，读未提交会出现脏读、不可重复读、幻读的问题，读已提交会出现不可重复读和幻读的问题，并发场景下的安全性太低。

串行化的隔离级别虽然最高可以避免脏读、不可重复读、幻读，但是它的并发性能太差了，所以一般很少使用。

而可重复读可以避免脏读和不可重复读，而且由于 InnoDB 的 MVCC、next - key Lock 等机制可以在很多场景下避免幻读，是并发安全和并发性能的平衡。

### 事务一般用在什么场景？

事务一般用于多个数据库操作之间需要保持一致性的场景，需要保证保证多个操作要么同时成功，要么同时失败，出现异常会回滚，不会影响到原数据。通常用于对多个表进行修改，多步骤写操作、核心业务状态变更的场景。



## MVCC

### MVCC 是什么？

MVCC 是多版本并发控制，是 InnoDB 用来提高读写并发性能的一种机制。它的核心思想是为数据保留多个版本，让普通查询可以读取符合当前事务视图的历史版本，从而避免读写操作频繁互相阻塞。

InnoDB 的 MVCC 主要依赖隐藏字段、undo log 和 ReadView。隐藏字段中比较重要的是 trx_id 和 roll_pointer，trx_id 记录最后修改该行的事务 ID，roll_pointer 指向 undo log 中的旧版本。undo log 保存数据修改前的历史版本，ReadView 用来判断某个数据版本对当前事务是否可见。

在读已提交隔离级别下，每次查询都会生成新的 ReadView；在可重复读隔离级别下，事务第一次查询时生成 ReadView，后续普通查询复用这个 ReadView，所以可以保证同一事务中多次查询结果一致。

MVCC 主要用于普通 select 这种快照读，而像 select for update、update、delete 这类读取最新数据并加锁的操作属于当前读。

### MVCC 解决了什么问题？

优先级：最重要

MVCC 主要解决的是数据库并发读写时的性能和一致性问题。如果没有 MVCC，读操作和写操作之间很容易互相阻塞，系统并发性能会比较差。

有了 MVCC 后，普通 select 可以读取某个历史版本的数据，而写操作可以继续修改最新数据，从而实现读写并发，提高性能。它让读操作不需要简单地依赖加锁来保证一致性，而是通过版本链和 ReadView 判断当前事务能看到哪个版本的数据。

简单来说，MVCC 的作用是：在保证一定隔离性的前提下，提高读写并发能力，减少读写阻塞。

关键词：**多版本并发控制、读写并发、减少阻塞、快照读、版本链、ReadView**

### MVCC 的实现原理大概是什么？

优先级：最重要

InnoDB 的 MVCC 主要依赖隐藏字段、undo log 和 ReadView。

每行记录中有两个重要隐藏字段：trx_id 和 roll_pointer。trx_id 记录最后一次修改这行数据的事务 id，roll_pointer 指向 undo log 中的旧版本记录。每次数据被修改时，InnoDB 会把修改前的数据保存到 undo log 中，多个历史版本通过 roll_pointer 串成版本链。

事务执行普通 select 时会生成 ReadView，ReadView 中记录了当前活跃事务的信息。查询某行数据时，InnoDB 会根据 ReadView 判断当前版本对本事务是否可见，如果不可见，就沿着 undo log 版本链继续向前找，直到找到一个可见版本。

关键词：**隐藏字段、trx_id、roll_pointer、undo log、版本链、ReadView、可见性判断**

### undo log 是什么？

优先级：最重要

undo log 是回滚日志，主要有两个作用：一是支持事务回滚，二是支持 MVCC。

当事务修改数据时，InnoDB 会先把修改前的数据记录到 undo log 中。如果事务需要回滚，就可以根据 undo log 把数据恢复到修改前的状态。对于 MVCC 来说，undo log 中保存了数据的历史版本，普通 select 可以根据 ReadView 沿着版本链读取可见的旧版本。

所以 undo log 不只是为了回滚，也是 MVCC 能实现快照读的重要基础。

关键词：**undo log、回滚日志、事务回滚、历史版本、版本链、MVCC**

### ReadView 是什么？

优先级：最重要

ReadView 是 InnoDB 在执行快照读时生成的一致性读视图，用来判断某个数据版本对当前事务是否可见。

ReadView 中会记录当前活跃事务 id 列表、最小活跃事务 id、下一个将要分配的事务 id 等信息。判断可见性时，会拿数据版本中的 trx_id 和 ReadView 中的信息进行比较，从而决定当前事务能不能看到这个版本。

在读已提交隔离级别下，每次普通 select 都会生成新的 ReadView，所以同一个事务中多次查询可能看到其他事务已经提交的新数据。在可重复读隔离级别下，事务第一次普通 select 时生成 ReadView，后续复用这个 ReadView，所以可以保证同一个事务中多次查询结果一致。

关键词：**ReadView、一致性读视图、活跃事务列表、可见性判断、读已提交、可重复读**

### 当前读和快照读的区别？

优先级：最重要

快照读是读取数据的历史可见版本，普通 select 通常就是快照读。它不会直接读取最新版本，而是通过 MVCC 和 ReadView 判断当前事务应该看到哪个版本，所以快照读一般不会加锁，读写并发性能更好。

当前读是读取数据的最新版本，并且通常会加锁，保证后续更新时数据是最新且安全的。比如 update、delete、insert、select ... for update、select ... lock in share mode 都属于当前读。

简单来说，快照读读的是符合当前事务视图的历史版本；当前读读的是最新版本，并且通常会加锁。

关键词：**快照读、当前读、普通 select、select for update、update、delete、MVCC、加锁**

### MVCC 能不能解决幻读？

优先级：普通

MVCC 可以在快照读场景下避免幻读。比如在 InnoDB 的可重复读隔离级别下，事务第一次普通 select 会生成 ReadView，后续普通 select 复用同一个 ReadView，所以即使其他事务插入了新数据，当前事务的普通查询也看不到这些新插入的数据。

但如果是当前读，比如 select for update、update、delete，这类操作需要读取最新数据并加锁，不能只依赖 MVCC。InnoDB 在可重复读隔离级别下通常会通过 next-key lock，也就是记录锁加间隙锁，来避免当前读场景下的幻读。

所以可以这样回答：MVCC 主要解决快照读下的幻读问题；当前读下避免幻读还需要依赖 next-key lock。

关键词：**快照读、当前读、幻读、可重复读、ReadView、next-key lock**

## 锁

### MySQL 中有哪些锁？

优先级：最重要

MySQL 中的锁可以从不同角度分类。

按锁粒度可以分为表锁、行锁。表锁锁住整张表，开销小但并发性能差；行锁锁住具体行，并发性能好但开销更大，InnoDB 主要支持行锁。

按锁模式可以分为共享锁和排他锁。共享锁也叫读锁，多个事务可以同时持有；排他锁也叫写锁，一个事务持有排他锁时，其他事务通常不能再加共享锁或排他锁。

InnoDB 行锁中还常见记录锁、间隙锁、临键锁。记录锁锁住具体索引记录，间隙锁锁住索引记录之间的范围，临键锁是记录锁加间隙锁，主要用于解决可重复读隔离级别下当前读的幻读问题。

关键词：**表锁、行锁、共享锁、排他锁、记录锁、间隙锁、临键锁、InnoDB**

### 表锁和行锁的区别？

优先级：最重要

表锁是锁住整张表，锁粒度大，加锁和释放锁的开销相对小，但并发性能差。一个事务对表加写锁后，其他事务对这张表的操作会受到较大影响。

行锁是锁住表中的某一行或某些行，锁粒度小，并发性能更好，但加锁和维护成本更高。InnoDB 主要使用行锁，适合高并发业务场景。

需要注意的是，InnoDB 的行锁是基于索引实现的。如果查询条件没有走索引，可能会扫描更多记录，导致锁范围扩大，甚至表现得像锁了很多行。

关键词：**表锁、行锁、锁粒度、并发性能、InnoDB、索引**

### 共享锁和排他锁的区别？

优先级：最重要

共享锁也叫 S 锁或读锁，多个事务可以同时对同一数据加共享锁，适合并发读取。一个事务持有共享锁时，其他事务可以继续加共享锁，但通常不能加排他锁修改这条数据。

排他锁也叫 X 锁或写锁，用于修改数据。一个事务持有排他锁时，其他事务通常不能再对同一数据加共享锁或排他锁，直到当前事务释放锁。

简单来说，共享锁之间兼容，排他锁和其他锁通常互斥。

关键词：**共享锁、S 锁、读锁、排他锁、X 锁、写锁、锁兼容**

### 什么是行锁、间隙锁、临键锁？

优先级：最重要

行锁更准确地说通常是记录锁，锁住的是某条具体的索引记录。比如根据主键 id = 1 更新一条记录时，InnoDB 会对这条索引记录加锁。

间隙锁锁住的是索引记录之间的间隙，不锁具体记录本身，主要目的是防止其他事务在这个范围内插入新数据，从而避免幻读。

临键锁也叫 next-key lock，是记录锁加间隙锁的组合，锁住某条索引记录以及它前面的间隙。在 InnoDB 可重复读隔离级别下，当前读经常通过 next-key lock 防止其他事务插入符合条件的新记录。

关键词：**记录锁、行锁、间隙锁、临键锁、next-key lock、索引范围、幻读**

### 什么是死锁？

优先级：普通

死锁是指两个或多个事务互相等待对方释放锁，导致大家都无法继续执行。

比如事务 A 已经锁住记录 1，准备去锁记录 2；事务 B 已经锁住记录 2，准备去锁记录 1。此时 A 等 B 释放记录 2，B 又等 A 释放记录 1，就形成了死锁。

InnoDB 可以检测死锁，一旦发现死锁，会主动回滚其中一个事务，让另一个事务继续执行。

关键词：**死锁、互相等待、锁资源、事务回滚、InnoDB 死锁检测**

### 如何避免或排查死锁？

优先级：普通

避免死锁可以从几个方面入手。

第一，尽量让多个事务按照固定顺序访问资源，比如都先更新用户表，再更新订单表，避免交叉加锁。

第二，事务尽量短，减少持有锁的时间，不要在事务中做耗时的外部调用。

第三，给查询条件建立合适索引，减少锁扫描范围，避免因为没有走索引导致锁住过多记录。

第四，必要时降低事务隔离级别，或者拆分大事务，减少锁冲突。

排查死锁时，可以查看 MySQL 的死锁日志，比如 `SHOW ENGINE INNODB STATUS`，分析哪两个事务、哪些 SQL、哪些索引发生了锁等待。

关键词：**固定加锁顺序、缩短事务、索引、减少锁范围、SHOW ENGINE INNODB STATUS、死锁日志**

## SQL 优化与 explain

### 如何优化一条慢 SQL？

首先通过慢查询日志或监控定位 SQL，然后用 explain 查看执行计划，重点看有没有走索引，扫描行数是否过多，访问性能是否较差，是否出现`Using filesort`、`Using temporary`。

优化是可以根据 SQL 写法和索引设计来入手，比如避免使用 `SELECT *`，给高频查询条件、排序、分组和关联字段建立合适的索引，避免在索引列上使用函数或者计算，遵循联合索引的最左前缀原则。对于深分页，可以考虑基于主键或上一页最后一条记录做分页优化。



### explain 是什么？

explain 是MySQL用来查看 SQL 执行计划的工具，可以用来查看一条 SQL 的执行计划，比如是否使用索引，使用了哪个索引，访问类型是什么，预估扫描行数是多少，以及是否出现额外排序或临时表。是分析慢 SQL 的常用工具。



### explain 中 type 字段怎么看？

type 字段表示表的访问类型，可以大致反映 SQL 的查询效率。常见的访问类型有 const、ref、range、index、ALL 等。一般来说，const 表示通过主键或唯一索引查询一条记录，效率很高；ref 表示通过普通索引进行等值查询；range 表示范围索引扫描；index 表示扫描整个索引；ALL 表示全表扫描，性能最差，需要重点关注和优化。

### explain 中 key 字段表示什么？

key 表示 MySQL 实际用到的索引。如果key 为某个索引名，说明优化器最终选择了这个索引；如果 key 为 NULL，通常表示没有使用索引。它和 possible_key 不一样，possible_key 表示可能使用到的索引，而 key 才表示最终实际使用的索引。

### explain 中 rows 字段表示什么？

rows 表示 MySQL 预估需要扫描的行数，是优化器根据统计信息计算出来的，不一定完全准确，一般来说，rows 越大说明扫描的数据越多，查询成本可能越高。分析慢 SQL 时，如果发现其 rows 很大就要考虑索引是否合适、条件区分度低、或者 SQL 写法导致没有有效过滤数据。

### explain 中 Extra 常见信息有哪些？

Extra 字段表示额外执行信息。常见的 Using index 通常表示使用了覆盖索引，是比较好的情况；Using where 表示还需要根据 where 条件过滤；Using index condition 表示使用了索引条件下推；Using filesort 表示需要额外排序；Using temporary 表示使用了临时表。分析慢 SQL 时，如果看到 Using filesort 或 Using temporary，通常要重点关注是否可以通过索引或 SQL 改写优化。

### 如何判断一条 SQL 有没有用到索引？

判断 SQL 是否用到索引，一般使用 explain。重点看 key 字段和 type 字段。如果 key 为 NULL，并且 type 是 ALL，通常说明没有有效使用索引，发生了全表扫描。

如果 key 显示某个索引名，并且 type 是 const、ref、range 等，通常说明使用了索引。

## 项目结合

### 项目中用到了哪些 MySQL 表？

优先级：普通

我的 UniTour 项目中 MySQL 主要用于存储核心业务数据，包括用户表、高校表、校区表、校园 POI 表、评价表、评价回复表、评价点赞表等。

用户表主要保存账号、手机号、密码、状态等信息；高校相关表保存高校基础信息、校区信息、校园 POI 信息；评价相关表保存用户对高校或校区的评分、文字评价、回复和点赞关系。

回答这个问题时不用把所有字段都背出来，重点说明：MySQL 负责保存项目核心持久化数据，Redis 主要用于验证码和高校详情缓存，OSS 主要用于图片等文件存储。

关键词：**用户表、高校表、校区表、POI 表、评价表、回复表、点赞表、核心持久化数据**

### 项目中的用户、评价、点赞、回复表是怎么设计的？

优先级：最重要

用户表主要保存用户账号信息，比如用户名、手机号、加密后的密码、用户状态、创建时间等。密码不会明文存储，而是通过 BCrypt 加密后保存。

评价表主要保存用户对高校或校区的评价内容，比如用户 id、高校 id、校区 id、评分、评价内容、创建时间等。这样可以根据高校 id 查询某个高校下的评价列表，也可以根据用户 id 查询用户发布过的评价。

点赞表主要保存用户和评价之间的点赞关系，一般会包含 user_id 和 review_id。为了防止同一个用户重复点赞同一条评价，可以对 user_id 和 review_id 建联合唯一索引。

回复表主要保存某条评价下的回复内容，一般会包含 review_id、user_id、回复内容、创建时间等。通过 review_id 可以查询某条评价下面的所有回复。

关键词：**用户表、评价表、点赞表、回复表、user_id、review_id、联合唯一索引、BCrypt**

### 评价点赞如何防止重复点赞？

优先级：最重要

评价点赞要同时从业务层和数据库层防止重复。

业务层可以在用户点赞前先查询当前用户是否已经点赞过这条评价，如果已经点赞，就直接返回提示，不再重复插入。

数据库层更关键，可以在点赞表中对 user_id 和 review_id 建联合唯一索引，保证同一个用户对同一条评价最多只能插入一条点赞记录。这样即使并发情况下两个请求同时通过了业务判断，数据库唯一索引也能兜底防止重复数据。

如果插入时发生唯一索引冲突，可以捕获异常并返回“已点赞”这类业务提示。

关键词：**重复点赞、业务判断、联合唯一索引、user_id、review_id、并发兜底**

### 为什么 review_like 表要对 review_id 和 user_id 建唯一索引？

优先级：最重要

因为点赞关系本质上是“一个用户是否点赞了一条评价”。同一个用户对同一条评价只能点赞一次，所以 review_id 和 user_id 的组合应该是唯一的。

对 review_id 和 user_id 建联合唯一索引有两个作用：第一，可以从数据库层面防止重复点赞，保证数据一致性；第二，可以提高查询点赞关系的效率，比如判断某个用户是否点赞过某条评价，或者查询某条评价的点赞记录。

业务层判断可以提升用户体验，但并发情况下仍然可能出现重复请求，所以最终要靠数据库唯一索引兜底。

关键词：**review_like、review_id、user_id、联合唯一索引、防重复点赞、数据一致性**

### 项目中哪些字段适合建立索引？

优先级：普通

项目中适合建立索引的字段主要是高频查询条件、关联字段、排序字段和唯一性约束字段。

比如评价列表经常根据 university_id 查询某个高校下的评价，所以评价表中的 university_id 适合建立索引。回复经常根据 review_id 查询，所以回复表中的 review_id 适合建立索引。点赞表需要根据 review_id 和 user_id 查询点赞关系，也需要联合索引或联合唯一索引。

用户登录时可能根据 username 或 phone 查询用户，所以用户名、手机号这类字段也适合建立唯一索引。

但索引不是越多越好，低区分度字段、频繁更新但很少查询的字段不适合随便建索引。

关键词：**高频查询、关联字段、排序字段、唯一约束、university_id、review_id、user_id、username、phone**

### 项目中分页查询是怎么做的？

优先级：普通

项目中的列表查询可以使用分页插件 PageHelper，也可以使用 MySQL 的 limit 语句实现分页。

如果使用 PageHelper，一般是在 Service 层查询前调用 PageHelper.startPage(pageNum, pageSize)，然后执行 Mapper 查询，PageHelper 会拦截 SQL 并自动添加分页语句，最后封装分页结果返回给前端。

分页查询要注意排序字段和索引设计。如果数据量比较大，深分页时 limit offset 很大可能会扫描大量数据，后续可以考虑基于上一页最后一条记录的 id 做优化。

关键词：**分页查询、PageHelper、limit、pageNum、pageSize、深分页、索引**

### 项目中有没有可能出现慢查询，如何优化？

优先级：普通

项目中可能出现慢查询的地方主要是高校详情聚合查询、评价列表分页查询、根据多个条件筛选高校等场景。比如评价表数据量变大后，如果没有给 university_id、review_id 这类高频查询字段建立索引，就可能出现扫描行数过多。

优化时可以先用慢查询日志或监控定位慢 SQL，再用 explain 查看执行计划，重点关注 type、key、rows、Extra 等字段。常见优化方式包括：避免 select *，给高频过滤和关联字段建立合适索引，遵循联合索引最左前缀原则，减少不必要的回表，对高校详情这种读多写少的数据使用 Redis 缓存。

如果是深分页问题，可以考虑基于主键 id 或上一页最后一条记录进行分页优化。

关键词：**慢查询、explain、索引、rows、Using filesort、Redis 缓存、深分页**

### 如果评价发布后需要更新高校评分，你会怎么保证数据一致性？

优先级：最重要

如果发布评价后需要更新高校评分，这里面至少涉及两个操作：插入评价记录，以及更新高校的评分统计。为了保证这两个操作要么都成功，要么都失败，应该放在同一个事务中处理。

在 Spring 项目中，可以在 Service 层方法上使用 @Transactional。先插入评价，再重新计算或增量更新高校评分，如果中间任何一步失败，就回滚事务，避免出现评价插入成功但高校评分没有更新的情况。

如果高校详情使用了 Redis 缓存，数据库更新成功后还需要删除对应高校详情缓存，让下次查询重新加载最新数据。这里一般采用“先更新数据库，再删除缓存”的策略。当前项目规模下这样就够了，如果后续并发更高，可以进一步考虑延迟双删、消息队列重试等方式增强一致性。

关键词：**评价发布、评分更新、@Transactional、事务、数据库一致性、删除缓存、Redis**
